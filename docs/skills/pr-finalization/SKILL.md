# PR Finalization

Prepare a change set for PR submission: complete the PR description against the target repo's real template, remove only diff-scoped noise (unnecessary comments, behavior-less tests), and prove nothing was lost. This skill prepares content; it never publishes anything.

## When to use

- The user asks to "finalize", "clean up", "polish", or "prepare" a PR.
- A PR description must be written or completed for an existing change set.
- A draft diff needs review for removable comment/test noise before submission.

Do NOT use when the task is to publish (open, comment on, review, or merge a PR), fix CI, or change behavior.

## Non-goals

- **No self-publishing.** The skill never creates, comments on, reviews, or merges a PR on its own, and never calls GitHub messaging APIs. Any `gh pr create/comment/review/merge` requires explicit user approval. Pushing branches is the orchestrator's responsibility per the repo workflow / user request — not something the skill does. Output is a completed description and a clean diff; the user or orchestrator publishes.
- No CI/coverage policy changes: never lower thresholds, disable jobs, or add skips.
- No behavioral code changes. The diff under review is frozen except for comment/test cleanup.
- No history rewriting: no rebase, amend, or force-push instructions.
- No work outside the diff under review; unrelated files are off-limits.

## Workflow

### 1. Discover the PR template (strict)

1. Identify the target repository (usually the workspace root).
2. If `.github/PULL_REQUEST_TEMPLATE.md` exists, it is authoritative — use it as-is.
3. Otherwise find the repo's actual template: case variants (`pull_request_template.md`), template files under `.github/`, `docs/`, or the repo root, or a template referenced by `CONTRIBUTING.md`, repo docs, or a recent merged PR body.
4. If the target repo is not the current workspace (e.g. finalizing a PR for a dependency or a linked worktree), read the **target** repo's template, never this repo's.
5. Only if no template exists anywhere, fall back to the built-in structure below and say so explicitly.

### 2. Strict completion

- Fill **every** section of the discovered template. No placeholder left as TBD.
- Keep the template's own headings and ordering; do not rename or drop sections.
- Verification must list exact commands with their real output.
- Do not invent required issue numbers; fill only fields the template itself asks for.

### 3. Diff-scoped comment cleanup

Only touch comments (and tests, section 4) inside the diff under review.

Delete:
- comments that merely restate the code
- outdated/misleading comments that no longer match behavior
- commented-out code blocks (dead code)

Keep:
- comments explaining **why** (rationale, trade-offs, non-obvious behavior)
- invariants, contracts, and safety properties
- SPDX license headers
- generated-code markers ("do not edit — generated by …")
- lint directives (`#[allow(...)]`, `// noqa`, `// nolint`, pragmas)

When a comment's intent is unclear, treat it as "why" until proven otherwise (see git blame check, section 6).

### 4. Test evidence gate

A test may be deleted **only** if every behavior it protected is still covered by a surviving test. Deletion is evidence-based, never count-based.

Eligible for deletion:
- exact duplicates of another test (name the surviving twin)
- implementation-detail or mock-only tests asserting nothing about real behavior
- assertion-free tests (no assert/expect/panic anywhere in the test)
- tautological tests (assert only what the code guarantees by construction)
- dead tests (not wired to any runner: wrong target, feature-gated off, never called)

For **each** deleted test, record:
- test name and file
- behavior(s) it protected
- surviving test(s) covering that behavior (name + file, or the exact assertion), verified by actually running them
- how it was verified (e.g. `cargo test <surviving_test>` output)

Forbidden as evidence:
- coverage percentages or line/function counts without named covering tests
- "the code is obviously fine"
- deleting because a test is slow, flaky, or annoying — that is a fix task, not a cleanup task

### 5. Hard keep list

Never delete, even with apparent coverage elsewhere:
- regression tests for fixed bugs (names often reference the bug/issue)
- boundary/edge-case tests (empty input, max values, off-by-one)
- protocol/wire-format tests (serialization, framing, API contracts)
- error-path tests (error codes, messages, failure handling)
- security tests (auth, injection, permissions, secrets)
- concurrency/race tests
- tests referenced by CI config, coverage config, or documentation

### 6. git blame/log safety check

Before deleting any comment or test:
- `git blame -L <start>,<end> <file>` on the lines to be deleted
- recent lines from the current change set that are pure noise → safe to delete
- old lines, or lines whose commit message records a bug fix, edge case, or a "why" → keep
- `git log --oneline -n 5 -- <file>` to check whether the surrounding area carries history worth preserving

If history is unavailable (shallow clone, brand-new file) or ambiguous, keep rather than delete.

### 7. Pre/post verification

Before cleanup, run the repo's own verification to establish the baseline (Rust repos: `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo build`; other repos: the equivalents in their docs/CI). Record results.

After cleanup, re-run the same commands. Results must be identical or better. Paste both runs into the Verification section.

Never:
- weaken CI jobs, coverage thresholds, or lint levels
- add `#[ignore]`, `#[cfg(any())]`, `skip`/`xfail`, or comment out a failing test to make CI green

### 8. Draft report before deletion

Before deleting anything, write a short working report:
- what will be deleted (file:line, test name)
- why it qualifies under sections 3–5
- which surviving test covers each protected behavior (names, not counts)
- verification plan

If the report cannot name covering tests, do not delete.

### 9. Produce the final PR description

Fill the discovered template with the final content. Summarize the cleanup (what was deleted and why) in What Changed, with the evidence table from section 4.

## Checklist

- [ ] Target repo's PR template read — never assumed to be this repo's
- [ ] Every template section completed; no TBD placeholders
- [ ] Diff-scoped comment cleanup: restating/outdated/commented-out code removed
- [ ] WHY / invariant / contract / SPDX / generated / lint-directive comments preserved
- [ ] Every deleted test has a named surviving test covering its behavior
- [ ] Hard-keep tests intact (regression/boundary/protocol/error/security/concurrency)
- [ ] `git blame`/log checked before deletions; ambiguous items kept
- [ ] Baseline verification ran before cleanup
- [ ] Verification re-ran after cleanup; exact commands + results recorded
- [ ] No CI/coverage thresholds lowered, no skips/ignores added
- [ ] Draft deletion report exists for every deletion
- [ ] No `gh pr create/comment/review` executed without explicit user approval
- [ ] Branch push left to the orchestrator / user per repo workflow; the skill did not push
- [ ] No GitHub messaging API calls made by the skill
